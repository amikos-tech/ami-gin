# Research: absent key vs explicit null in predicates

Question: should `IsNull(P)` match absent documents in every case (A), or should it keep "explicit null only" with a separate absent operator (C)? Researched 2026-10-06.

Legend: "absent" = key not in the document; "null" = key present with JSON `null`.
"UNVERIFIED" = taken from memory or secondary sources and not confirmed against the official page during this research.

## 2. Families

1. **Collapse absent into null ("null-or-missing")**: MongoDB `{f:null}`, ClickHouse JSON, Parquet/Iceberg/Delta schema evolution, and the SQL scalar extractors (`->>`, `JSON_VALUE`, DuckDB `->>`). The default user-visible "is null" covers both states. Most of these also give a narrower tool (`$type:"null"`, `->` / `JSON_QUERY`, `?`, `$exists`) for the rare case that needs the difference.
2. **Three-state null / missing / valued**: Couchbase (`IS NULL`, `IS MISSING`, `IS VALUED`), Snowflake (`IS_NULL_VALUE` vs `IS NULL`). Each state has its own predicate. Snowflake documents the JSON-null vs SQL-NULL confusion and recommends `STRIP_NULL_VALUES` when null "indicates missing values and has no other special meaning".
3. **No null at all; empty = missing**: Prometheus (and Loki, UNVERIFIED). An unset label and `""` are the same value. `!=` matches absent series.
4. **Null not indexed; "exists" is the only primitive**: Elasticsearch/OpenSearch. Explicit null and absent are the same unless the mapping sets `null_value`. "Missing" is `must_not exists`, so it covers both.

## 3. Lessons and gotchas

- **MongoDB surprise, then narrowing**: `{f:null}` matching absent docs is a well-known surprise. The docs keep a full tutorial page for it. 8.0 narrowed it: equality to null no longer matches the deprecated `undefined` BSON type ([8.0 compatibility](https://www.mongodb.com/docs/manual/release-notes/8.0-compatibility/)). The current tutorial also notes a 9.0 change: a dotted path through arrays that does not resolve to a non-null value now evaluates as `null`. That widens null-or-missing further. The "absent counts as null" rule itself was kept.
- **MongoDB `$ne` includes absent docs.** The docs call this out with an example ("returns movies even when the rating data is unavailable"). So `$ne:"G"` ∪ `{rated:null}` is redundant on absent docs. This is the same as TCLR's `NE ∪ IsNull` idiom.
- **Snowflake JSON null vs SQL NULL**: `IS NULL` misses JSON nulls. Users must use `IS_NULL_VALUE` or cast to text. Snowflake's own advice is to strip JSON nulls at load time when they mean "missing", which in effect collapses the two states.
- **ClickHouse chose to lose the distinction** to get a columnar layout. The docs say it is "impossible to determine" whether the source had a null or no key.
- **Prometheus `!=` matches unset labels**, and `{env=""}` matches series without `env`. The docs state: "Label matchers that match empty label values also select all time series that do not have the specific label set at all." This is the model closest to TCLR log labels.
- **Elasticsearch**: `exists` is false for `null` and `[]`. Users who need explicit null must configure `null_value` at mapping time.
- **SQL-family `!=` drops NULL rows** (PostgreSQL, Couchbase, ClickHouse, Snowflake, DuckDB, BigQuery). This is why users write `x <> 'v' OR x IS NULL`, the same shape as TCLR's `NE ∪ IsNull`.
- **Iceberg pruning**: a file that lacks a column reads it as all-null (or `initial-default`). So an `is_null` pruner must keep files where the column is missing. Treating "missing column" as "no nulls" is a pruning bug class (UNVERIFIED: no specific issue link found during this research).

## 4. Implications for ami-gin (A vs C)

- **Prevailing convention**: most systems that users reach through a "null" predicate treat absent as null (MongoDB, ClickHouse, Iceberg/Delta schema evolution, SQL `->>` / `JSON_VALUE`, Elasticsearch "missing"). Only Couchbase and Snowflake expose a strict three-state model, and both add dedicated operators (`IS MISSING` / `IS VALUED`, `IS_NULL_VALUE`), not one overloaded `IS NULL`.
- **Option (A) uniform**: this matches MongoDB `{f:null}` and the SQL `->> IS NULL` idiom. It also matches TCLR's intent ("label not set"). For a pruning index it is the safe direction: if a caller wanted "explicit null only", (A) over-selects, which costs time but never loses rows. It also removes the current inconsistency (absent counts only when an RG holds 2+ docs).
- **Option (C)**: this matches Couchbase/Snowflake. It needs a new operator, and TCLR must change `NE ∪ IsNull` to `NE ∪ IsNull ∪ IsMissing`, or else row groups whose docs only lack the label are wrongly pruned. Under (C), an index that cannot see absence per document must still over-select on IsMissing to stay correct.
- **Precedent for both**: MongoDB pairs a broad null (`{f:null}`) with narrow tools (`$type:"null"`, `$exists`). If a strict "explicit null only" predicate is ever needed, a later additive operator (for example `IsNullValue`) would follow that pattern without breaking the broad default.
- **NE and absent (report only)**: there is no single convention. MongoDB `$ne`, Elasticsearch `must_not term`, and Prometheus/Loki `!=` match absent docs. All SQL-family systems (PostgreSQL, Couchbase, ClickHouse, Snowflake, DuckDB, BigQuery, SQL/JSON) do not match absent or null, because of three-valued logic. ami-gin's current NE (path must be present) follows the SQL family, and TCLR's `NE ∪ IsNull` is the standard SQL workaround. That workaround is only complete if IsNull covers absent in every case, which is the argument for (A).
