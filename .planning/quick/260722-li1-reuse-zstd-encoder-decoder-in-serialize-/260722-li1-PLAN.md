# Quick Task: Reuse zstd encoder/decoder in serialize.go

## Problem (issue #43)

`Encode` allocates ~589 MB/op serializing a ~100 KB index because `serialize.go`
constructs a fresh `zstd.NewWriter` on every call. Memory profile attributes 97%
of allocations to the encoder constructor; allocation scales linearly with
`GOMAXPROCS` (53 MB @1 core → 588 MB @16), because `NewWriter` defaults concurrency
to one encoder state per core. `Decode` has the same construct-per-call pattern
with `zstd.NewReader`.

## Fix

In `serialize.go`, add lazily-initialized, mutex-guarded package-level caches:

- `sharedZstdEncoder(level CompressionLevel) (*zstd.Encoder, error)` — one encoder
  per level, created with `WithEncoderLevel` + `WithEncoderConcurrency(1)`, cached
  in a `sync.Mutex`-guarded `map[CompressionLevel]*zstd.Encoder`.
- `sharedZstdDecoder() (*zstd.Decoder, error)` — one shared decoder via `sync.Once`,
  created with the existing `WithDecoderMaxMemory` / `WithDecoderMaxWindow` /
  `WithDecodeAllCapLimit(true)` safety limits.

Replace the per-call constructions in `encodeWithLevel` and `Decode` with the
shared getters. `EncodeAll`/`DecodeAll` are documented concurrency-safe, so shared
instances are safe. Never `Close()` the shared instances.

### Invariants preserved

- Public API unchanged.
- Decoder safety limits (`maxDecodedIndexSize` memory/window + cap limit) unchanged.
- The `make([]byte, 0, maxDecodedIndexSize)` dst buffer stays per-call (a shared
  mutable output buffer would race; the cap also enforces the decode-bomb limit).

## Verification

- `go build ./...`, `go vet ./...`
- `go test ./...` (serialize round-trip, decode-limit, and property tests)
- `go test -run '^$' -bench 'BenchmarkPhase20RealisticJSON/.../Encode' -benchmem`:
  Encode B/op ~589 MB → near-zero steady state, ns/op improved.
